# Reader batch ownership through transaction failure

`Reader.pass` previously removed its pending actions and local notices before
opening the SQLite transaction. If `BEGIN` or the journal query failed, the
worker kept its old state, but those shared arrays stayed empty. A queued
`Community.found` intent was never invoked and produced no result.

The pass now observes its initial batches without removing them. After the
transaction and journal read succeed, it removes only the captured action
prefix. New actions stay queued for the next database snapshot. Local notices
remain queued until successful `COMMIT`; acknowledgement removes only the
original notice prefix, excluding notices generated by actions or later
producers. A revoked pass closes its transaction before returning and retains
the existing per-action cancellation checks.

This uses the active reader lifetime's existing ownership: one reader consumes,
frame producers append, and teardown detaches that Shared before starting a
replacement with a fresh Shared. The post-journal cancellation check is not an
atomic teardown barrier. Partial action/outbox/completion effects after claiming
and outer App-state rollback remain separate, unproved boundaries. No queue
capacity, eventual database success or whole-action completion theorem follows
from this repair.

The actual SQLite regression had seven passes and four failures before repair.
It now passes 29 checks covering journal failure, actual failing `BEGIN`, a
failed query over pending data, action and notice arrivals after a SQL snapshot,
and cancellation followed by a fresh reader lifetime. The late action reads
`new` on the next snapshot while the original action reads `old`. The old
nine-check reader/pruner regression and App proofs also pass with this change.

Five controls compile the actual changed reader: early batch claim, discarding
later actions, early notice acknowledgement, acknowledging uncaptured notices,
and leaking the canceled transaction. Each must fail its exact expected
assertion set; compiler errors, crashes and timeouts are failures of the gate.
The restored source passes all 29 checks. This is native regression evidence,
not a kernel proof of SQLite or asynchronous worker execution.

`mise run test:reader-claim` sets up an isolated source/build snapshot, builds
under the 48 GiB/no-swap cap, runs the checks and controls, and preserves logs
and databases in `out/reader-claim/negative`. Engine CI invokes the same named
task. The ready bootstrap workflow retains those artifacts; hosted workflow
activation remains outside this milestone. Integrated-tree validation passes: all 1,294 audited laws, 670 inventory/README
references, the named 29-check/five-control task, reader/pruner 9/0 plus its
control, 82 demand and 34 component checks, and lifecycle 39/0. The first
lifecycle run exposed a fixture tied to enabled-poll count: the new earlier
cancellation guard moved its revocation before its intended second query.
The fixture now revokes through the existing `afterQuery` hook after the actual
second SQL/cache read, independently of lease-poll frequency. Both compiled
read-after-revoke and publish-after-revoke controls reject their faults, and
the restored lifecycle suite passes. Original failure and repaired evidence
remain in `out/ci/reader-claim-{integrated,lifecycle-fixed}.log`.
